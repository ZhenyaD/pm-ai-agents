7. Flow markers above each screenshot must use BPMN-style notation, not a plain circle for every step:
   - Oval/circle (thin border) = start event / entry point of the flow
   - Oval/circle (thick border) = end event / end of the flow
   - Oval/circle (double border) = intermediate event, e.g. waiting for an API response after a user click
   - Square / rounded rectangle = a user action (a click, input, selection) — this is the main element type, since a UI flow exists to represent user actions
   - Diamond (ромб / rhombus) = a gateway/branch point where the flow splits into multiple paths, e.g. the happy path continuing in one direction with an edge case branching off below it via its own arrow

7a. Established visual style (confirmed working well, keep reusing across all UI-flow builds unless told otherwise):
   - Canvas fill: dark gray, RGB (0.118, 0.118, 0.118) — Figma's default dark canvas color.
   - BPMN shape stroke: light gray, RGB (0.85, 0.85, 0.85), 2px weight (thick end-event circles: 4px).
   - BPMN shape fill: RGB (0.16, 0.16, 0.16) for rects/diamonds; circles unfilled (transparent) so the canvas shows through.
   - Layer 1 connector arrows: orange/amber, RGB (0.95, 0.65, 0.2), 2px weight, single arrowhead at the destination end only (build as a vector with per-vertex `strokeCap`: `NONE` on the start vertex, `ARROW_EQUILATERAL` on the end vertex — do not use a uniform `strokeCap` on a `LineNode`, which arrows both ends).
   - Labels: white text, Inter, 11px, centered under/above their shape.

8. Screenshots must be REAL captures of the actual product pages — never hand-rebuilt using Figma rectangles/text/auto-layout components made to look like the page. Recreating a screen with primitives is explicitly wrong even if it looks accurate; it is not a "screenshot." Single-viewport screenshots (not the full scrollable page) are the accepted default — the user has explicitly confirmed one-screen-at-a-time captures are fine; don't hold up the flow chasing full-page capture.

   - **Primary method — proven, fully automatic, no installs needed (use this by default):**
     1. Navigate to the target URL in a `claude-in-chrome` tab, wait for load.
     2. `gif_creator` action `start_recording` (tabId) → immediately `stop_recording` (tabId) with no/minimal actions in between, so it captures a single frame of the current viewport.
     3. `gif_creator` action `export` with `download: true`, a `filename`, and `options: {showClickIndicators:false, showDragPaths:false, showActionLabels:false, showProgressBar:false, showWatermark:false}` (required — see point 9). This downloads a real file to `~/Downloads/<filename>.gif`, which — unlike `computer` tool's `save_to_disk`, which is NOT retrievable from the local filesystem — is a real file Bash can read.
     4. Convert GIF → PNG with macOS's built-in `sips` (no extra installs): `sips -s format png ~/Downloads/flow_1.gif --out ~/Downloads/flow_1.png`.
     5. Create the target image-fill node on the Figma canvas first (sized/positioned per point 16), then call the Figma MCP's `upload_assets` (`fileKey`, `count`, `nodeId`, `scaleMode`, e.g. `"FILL"`) to get a `submitUrl` per asset.
     6. `curl -s -X POST "<submitUrl>" -H "Content-Type: image/png" --data-binary @~/Downloads/flow_1.png` to upload the bytes — Figma places the image on the node. Run uploads for multiple screens in parallel (background `&` + `wait`).
     - See `feedback_real_screenshot_capture_method` memory for the full worked recipe/history.
   - **Fallback — Figma's own capture tool (only if the primary method is insufficient, e.g. full-page really is required):** call `generate_figma_design` with the target `fileKey`. For localhost/dev-server targets this works standalone. For external sites it requires a **Playwright MCP server** — check `claude mcp list` first, and do not silently install Node.js/Homebrew to get it running (that's a system change requiring explicit user confirmation).
   - **Manual hand-off (last resort):** ask the user to capture the URLs themselves and drop image files somewhere you can read them, then import via `upload_assets`/`curl` as above without redrawing them.
   - Chrome extension UI (toolbar icons, extension popups) and native OS screenshot tools are **not reachable** by the `claude-in-chrome` browser-automation tool (it only sees in-page content, not browser chrome) — don't waste time trying to click an extension icon or trigger OS-level screenshot shortcuts. macOS also has no built-in full-page capture for arbitrary Chrome content (that's a Safari-only feature).

10. There are TWO separate wire/connection layers in the file, complementing each other — do not conflate them:
    - **Layer 1 — BPMN flowchart wires (top):** a simplified flowchart connecting the BPMN shapes themselves (circle → diamond → square → square → diamond → ... → circle) with directional arrows, so the viewer can trace the abstract flow independently of the screenshots.
    - **Layer 2 — UI hotspot wires (bottom):** separate prototype connections between the actual clickable elements across the screenshots/mockups themselves (see point 14), so the visual mockups form their own click-through prototype.

11. Layer 1 must be connected by directional arrows in sequence (start circle → gateway diamond → action shape → action shape → gateway diamond → ... → end circle), so the viewer can visually trace the flow — not just placed side by side as disconnected icons. See the reference file for the exact pattern: `.claude/knowledge/design/ui-flow-examples/UI_flow.png` (zoom into the top-left ~6000x500px region to see the connector style clearly).

12. Every BPMN shape has a short description of the user's action/state directly below it (in addition to any diamond branch labels below/above, per point 13), matching the naming style in `UI_flow.png`:
    - **Circle (event):** named as something that already happened, past tense, from the user's perspective — e.g. "A user opened the page", "A user added something to the cart". Events describe a state change, not an instruction.
    - **Square/rounded-rectangle (action):** named as an instruction/imperative describing what the user must do — e.g. "Open the browser tab", "Click the button". Actions describe what to perform, not what happened.

13. Label placement on the BPMN row:
    - Below a rounded-rectangle/pill (user action) shape: the action taken, e.g. "Click the 'Find quote' button" (see point 12 for naming style)
    - Above a gateway diamond: the condition that continues the main/happy path, e.g. "Quote redemption is enabled for a user"
    - Below a gateway diamond: the condition that branches off into an edge case, e.g. "Quote redemption is disabled for a user"

13a. **Every BPMN shape needs exactly one screenshot below it — there is no such thing as a marker with no screenshot.** This is the most important structural rule and the one most likely to be gotten wrong:
    - **Circles and diamonds (events/gateways) show STATE** — place the plain screenshot of that page/moment with no added highlight (e.g. "Search results finished loading" → the search results screenshot, untouched).
    - **Rounded rectangles (actions) show the element to click, highlighted, on the SAME screenshot the action happens on.** Take the screenshot of whichever page the click happens on (reuse/duplicate the same image used by the preceding or following state if it's the same page — see point 3), then draw a visible highlight box directly on top of the real clickable element inside that screenshot instance: no fill or a faint tint (e.g. `{r:1,g:0.8,b:0.3}` at ~18% opacity), a 3px stroke in the same orange as the Layer 1 connector arrows (point 7a), rounded corners. The static diagram must be understandable on its own — someone looking at the image (not just playing the prototype) should immediately see what gets clicked.
    - Concretely, for a page visited across multiple consecutive steps (e.g. the homepage, or a PDP before/after a selection), duplicate that screenshot once per step that references it — one plain instance for the "arrived at this state" event, one highlighted instance per action taken on it — rather than skipping the screenshot for action steps.

14. When a gateway diamond has an edge-case branch, draw a straight line/arrow from the diamond down to a separate sub-flow beneath the happy-path row — its own small chain of shapes and screenshots for that edge case — rather than only describing edge cases as plain text notes underneath the happy path. See point 16 for exactly where this branch is allowed to drop down so it never crosses a screenshot.

15. Layer 2 (see point 10): wire real Figma prototype connections, not just a static image flow — overlay a transparent hotspot frame on the actual clickable element in each screenshot (e.g. the "Add to cart" button's position) and set a click reaction via `node.setReactionsAsync()` navigating to the next screen's frame. This lets the file be played as a click-through prototype in Figma's Prototype tab with visible hotspots, matching real product click-through demos. The Plugin API supports this (`ReactionMixin` / `setReactionsAsync` on frames) — attempt it by default rather than treating it as unsupported.
    - **The click-through chain must cover every single step, start to end — not just a handful of "anchor" screens.** If there are 13 BPMN shapes there are 13 chained reactions (12 links), one from each screenshot instance to the next, so playing the prototype end-to-end walks through the entire happy path exactly as a real user would, one click per step.
    - Hotspot placement per step type: on an **action** step, the hotspot is the *same* highlighted region drawn per point 13a (the real clickable element) — clicking the visible highlight is what advances the prototype. On a **state/gateway** step (circle/diamond, no specific click target), the hotspot covers the *entire screenshot* as a "continue" click, since the point of that step is just to advance past a state, not to click something specific.
    - Gateways only need the happy-path reaction wired into the click-through chain (advance to the next happy-path step). The edge-case branch shown in Layer 1 is a visual/diagrammatic branch, not a second interactive path from the same click — don't try to give one hotspot two destinations.
    - `setReactionsAsync` NAVIGATE destinations must be **top-level frames directly on the page** — not nested inside a Group or Section. Keep every screenshot frame and every hotspot's containing frame flat at the page level (never wrap the finished flow in a Group for tidiness or for taking a single overview screenshot; if you must group temporarily to render one overview image, ungroup again immediately afterward before doing any further reaction wiring).
    - Hotspot rectangles must be **nested inside their source screen's frame** (as a child, positioned with `layoutPositioning = "ABSOLUTE"`), not left as a loose rectangle parented directly to the page — a page-level rectangle is rejected as "not a valid prototype source." Screenshot images themselves must also be wrapped in a Frame (not a bare Rectangle/image-fill node) so hotspots have somewhere to nest and the frame itself can be a NAVIGATE destination.

16. **Layout / spacing algorithm (critical — get this right, it's the most common mistake):**
    - Exactly **one BPMN marker sits directly above exactly one screenshot**, horizontally centered on it, for EVERY shape (see point 13a — there is no "markerless gap" anymore now that every shape has its own screenshot). Never place more than one marker (event/action/gateway) in the horizontal span of a single screenshot. **Exception: gateway diamonds with an edge-case branch — see the dedicated bullet below.**
    - Lay the happy path out as **uniform fixed-width columns**, one per BPMN shape, each as wide as the screenshot (e.g. 1456px for a desktop capture) plus a modest fixed gap to the next column (e.g. ~150–200px — just enough for the connector arrow and label spacing). With N shapes in the main chain, that's N columns at a constant pitch — don't vary the spacing per step.
    - **Gateway diamonds that have an edge-case branch are the one shape that does NOT stay centered over its own screenshot** — shift it sideways into the empty **gap immediately after** its screenshot (gap-center x = that screenshot's right edge + half the inter-column gap), rather than centered on it. Its screenshot still stays in its normal uniform-grid column (see previous bullet); the marker is what moves. This is what lets its branch drop as a single **straight vertical line** with zero jog: since the gap contains no screenshot at all, a plain vertical arrow from the diamond straight down to the edge-case row can never cross one. (Gateways with no edge branch stay centered as normal — this exception only applies when there's a branch to route.)
    - **Routing the branch itself (table/grid layout, not a diagonal):** draw one straight vertical arrow from the shifted diamond down to the edge-case row's y-level, then a second straight horizontal segment at that row to reach the x-position of whatever shape sits in the **next column of the main row** (i.e. the shape immediately following the gateway in the happy-path chain) — the edge-case's first shape (usually an action) is placed centered at that same x, directly beneath that main-row shape, "one beneath another," like a table cell. Do not use a diagonal or an elbow that jogs before reaching the bottom row — vertical, then horizontal, full stop.
    - The reference file `.claude/knowledge/design/ui-flow-examples/UI_flow.png` shows the general spirit of this (straight, traceable lines, no zigzag, grid-aligned rows) — no connector line should ever cross through a screenshot that isn't the one it's leaving from.

19. **Browser navigation efficiency (critical — this has caused a run to be killed for being too slow):** never drive a page by "screenshot → guess a click coordinate → wait → screenshot again." Use `find` / `get_page_text` / `read_page` first to locate real elements (login fields, search box, product links, add-to-cart button, checkout form fields), and click against what those return. Only take a screenshot to (a) capture the final artifact image per point 8, or (b) sanity-check a page once per major navigation — never once per click. When retyping a text field after a failed attempt (e.g. a login that didn't take), select-all/clear it first; don't append blindly and then manually verify by counting characters.
